# Project Report Notes

## Title
AI-Based Self-Healing Cloud Infrastructure for Automatic Server Failure Detection and Recovery

## Abstract
Cloud-hosted applications depend on service availability and predictable response times. This project demonstrates a self-healing workflow that records service metrics, estimates failure risk with a Random Forest classifier, detects threshold violations, creates alerts, and executes a controlled recovery action. A React dashboard communicates with a Flask REST API, while SQLite stores service records, metric history, predictions, alerts, settings, and recovery logs. The included recovery adapter is deliberately simulated: it restores demo metric values and verifies that those values satisfy configured thresholds. The model is trained and evaluated on generated synthetic data, so the evaluation report demonstrates implementation methodology rather than real-world failure prediction performance. The project provides a reproducible base for future integration with real monitoring and a tightly allowlisted cloud/container recovery adapter.

## Problem Statement
Threshold-based monitoring can identify some unhealthy conditions but does not, by itself, provide an integrated workflow for risk estimation, incident logging, recovery attempts, and post-recovery verification. The project implements these steps in one demonstrable system while distinguishing simulated behaviour from real infrastructure operations.

## Objectives
1. Store service health metrics and history.
2. Estimate failure risk from CPU, memory, disk, response-time, and error-rate features.
3. Detect configured warning and critical thresholds.
4. Record alerts and recovery events.
5. Apply a controlled recovery adapter and verify the final state.
6. Present service status, predictions, alerts, and logs in a web dashboard.
7. Test positive and negative recovery outcomes.

## Existing System
Basic monitoring tools often report threshold violations and leave recovery orchestration to separate scripts or an operator. This prototype's earlier implementation also had a dashboard, seeded server records, a Random Forest model, and a recovery button, but model inference was not integrated into the main workflow, the monitoring/recovery modules were empty, and the recovery operation immediately reset values without a real verification step.

## Proposed System
The revised project integrates a Flask API, SQLAlchemy/SQLite persistence, a Random Forest prediction module, threshold-based monitoring helpers, a simulated recovery adapter, and a multi-view React dashboard. An incident is logged, a prediction is stored, and a recovery result is determined by checking the restored metrics against configured thresholds. A failed-recovery test path verifies that a service is not marked Healthy when verification fails.

## Modules
1. **Authentication:** session-based local administrator login and hashed password verification.
2. **Server Management:** create, list, update, and delete monitored service records.
3. **Monitoring:** store metrics, evaluate thresholds, and avoid duplicate unresolved alerts for the same service/title.
4. **AI Risk Assessment:** Random Forest prediction using five metric features; stores risk history and model evaluation.
5. **Failure Simulation:** generates repeatable high-CPU, high-memory, high-latency, high-error, and unavailable-service scenarios.
6. **Recovery Management:** records attempts, restores simulated metrics when allowed, and verifies health.
7. **Alerts and Logs:** displays open/resolved alerts and historical recovery events.
8. **Settings:** persists warning/critical thresholds and automatic-recovery configuration.
9. **Dashboard:** refreshes API data and presents summary counts and service state.

## Technology Stack
- Frontend: React, JavaScript, Vite, CSS
- Backend: Python, Flask, Flask-CORS, Flask-SQLAlchemy
- Database: SQLite
- Machine learning: NumPy, scikit-learn Random Forest, Joblib
- Testing: pytest
- Optional container setup: Docker Compose

## AI Methodology
A reproducible synthetic dataset is generated from random resource metrics. Labels are assigned using documented threshold combinations. Data is split into training and held-out test partitions, then a Random Forest classifier is trained. The project records accuracy, precision, recall, F1-score, confusion matrix, and feature importance in `backend/model_metrics.json`. Because the labels are generated by the same synthetic rules, the metrics do not establish performance on actual cloud incidents. Real validation would require representative time-series telemetry and incident labels.

## Database Schema
- `users`: administrator username and password hash (credentials are environment-managed).
- `servers`: current service metrics, status, and latest AI score.
- `metrics`: timestamped metric history by service.
- `predictions`: probability, risk category, model identifier, explanation, and timestamp.
- `alerts`: severity, message, resolution state, and timestamps.
- `recovery_logs`: recovery/incident event and result.
- `app_settings`: JSON-encoded configuration values and update time.

## Testing

## Limitations
The project uses simulated service metrics and a simulated recovery adapter. It does not connect to AWS, Azure, Kubernetes, Prometheus, or remote service endpoints. The classifier uses synthetic labels rather than a real-world incident dataset. The local admin session is for a student demonstration and requires additional hardening before deployment.

## Future Enhancements
- Collect actual metrics from a configured health endpoint or Prometheus/CloudWatch.
- Integrate a dedicated, least-privilege adapter for an explicitly allowlisted test container or cloud resource.
- Validate the ML model on real labelled incidents and time-aware splits.
- Add role-based user management, CSRF protection, HTTPS, alert notifications, and audit retention.
- Deploy the app in a monitored container environment.

## Conclusion
The project demonstrates an end-to-end pattern for monitoring, AI-assisted risk estimation, alert generation, controlled recovery, and post-recovery health verification. Its explicit simulation boundaries make it suitable for a safe local demonstration and as a foundation for further cloud integration.
